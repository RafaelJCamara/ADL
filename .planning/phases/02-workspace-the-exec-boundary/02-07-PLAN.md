<objective>
Give the worker a real OS identity: on Linux, every child ADL launches runs as a dedicated unprivileged user through a launcher that drops supplementary groups properly, with a scratch HOME and worktree it can write and a main repository configuration it cannot — and everywhere else, say plainly that it does not.

**MVP user story** (from ROADMAP.md § Phase 2 success criterion 4): **As a** maintainer deciding whether to install a daemon with repository write access, **I want to** see the agent running as a separate unprivileged OS user that cannot touch my repository's configuration, **so that** the blast radius of a hostile spec is bounded by the operating system rather than by ADL's own care.

Purpose: `02-RESEARCH.md § Pitfall 8` shows why the obvious implementation is wrong twice over — the child-process uid and gid options need a root caller and do not drop supplementary groups, so the "unprivileged" worker inherits memberships silently. D-18 resolves this to `sudo -u` as the default launcher with `setpriv --init-groups` documented as an alternative, both OS-gated, degrading to a warning rather than a hard failure. `§ Pitfall 5 layer 2` supplies the other half of what a dedicated user actually buys: the main repository's configuration file becomes unwritable by the agent.

Output: the privilege module, the visible-skip helper, the install documentation that states the sudoers requirement rather than hiding it, and the CI provisioning that makes the Linux-only assertions execute instead of skip.

**D-21 applies to this plan more than any other.** Two of its acceptance criteria cannot run on the Windows development machine. They must skip with a stated reason rather than pass, and the phase is not done until they have run green on Linux.
</objective>

    Export a `PrivilegeMode` describing the three outcomes: dropped (a launcher was found and a worker user is configured), unsupported-platform, and launcher-missing. Gate everything on the platform being Linux — on any other platform the mode is unsupported-platform and the prefix is empty.     Export `applyWorkerAccess(paths, config)`. When the mode is dropped, it sets the group of each supplied directory tree to the configured shared group and adds group read, write, and traverse permission, so the worker user — a member of that group — can use its scratch HOME and write inside its own worktree. It must apply to the scratch HOME, the worktree directory tree, and the main repository's per-worktree administrative directory (the worker needs to write an index and a HEAD there to commit). It must **not** apply to the main repository's configuration file, which stays owned by the daemon user and group-readable but not group-writable — that restriction is precisely what a dedicated OS user buys beyond "the agent cannot read the shadow file", and it is the structural half of the defence against the shared-configuration code-execution path. When the mode is not dropped, `applyWorkerAccess` is a no-op. Setting a group requires the calling process to be a member of it, which the install documentation establishes; a failure to set it is reported as a degraded mode with a named reason rather than swallowed.

The worktree backend calls `applyWorkerAccess` after creating the worktree and the scratch HOME. Read the worker user and shared group from configuration passed into the backend factory, defaulting from the `ADL_WORKER_USER` and `ADL_WORKER_GROUP` environment variables of the **daemon's** process — this is the one place the daemon's own environment is legitimately read, and it reads two non-secret names, never a credential.

    Take care that the launcher prefix interacts correctly with the zero-inherit environment: `sudo` resets the environment by default, so the invocation must be constructed so the child receives the environment the builder produced rather than a sudo-sanitised one. Verify the behaviour empirically on the Linux CI run rather than assuming it, and record what you observed in the plan SUMMARY.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| daemon OS identity → agent OS identity | Without a privilege drop these are the same identity, so everything the daemon can reach — its own credentials on disk, its configuration, the whole home directory — is reachable by anything the agent runs. |
| worker user → main repository administrative files | The worker must write its own worktree and its per-worktree git administrative directory, and must not write the repository configuration that decides which programs git executes. |
| CI configuration → evidence | A gate whose test skipped is a gate that produced no evidence, and a skipped test in a green log is indistinguishable from a passing one. |
