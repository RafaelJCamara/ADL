<objective>
Make swappability provable rather than asserted: two backends registered under one named registry, both passing one parameterised contract suite, with the registry as the only place either implementation is named — and close the interface-level containment D-02 requires.

**MVP user story** (from ROADMAP.md § Phase 2 success criterion 3): **As a** maintainer who will eventually want container-per-feature isolation, **I want to** see a second workspace backend already running the same code paths with zero call-site edits, **so that** the v2 container backend is a registry entry rather than a repository-wide sweep.

## Assumption-Delta checkpoint — outcome

The deterministic detector fired on a `pluralization` signal in success criterion 3: the term **"second"**, in *"A second workspace backend is registered and the loop runs against it unchanged."* A core assumption has lost its monopoly.

**The noun that is now primary:** `Workspace` — the registry-resolved backend, addressed by a string id. It is no longer "the workspace" (singular, implicitly the git worktree); it is one of a set.

**Decision: `promote`.** `Workspace` is promoted to the primary representation and `WorktreeWorkspace` is demoted to a *detail of one variant* — the implementation registered under the id `'worktree'`, with no privileged position in any type, any call site, or any test. `'stub'` sits beside it as a peer, and v2's `'container'` will be a third peer added by registration alone.

**This is not a new decision — D-04 already pointed at promote.** D-04 locks a named registry resolved once at manager startup from daemon config, mirroring Phase 1's D-23 harness registry. A registry keyed by id *is* the generalized representation; adding the stub alongside a still-privileged worktree type would have contradicted the decision the user already made. Saying so explicitly rather than leaving it implied is the point of recording this: the demotion is the work, not a side effect.

**What promote costs, concretely, in this plan:** the worktree backend gains no method the interface does not declare; no consumer imports `worktreeWorkspace` directly; and the contract suite is written against the interface with no `if (id === 'worktree')` anywhere.

**Invariant test encoding the generalized intent** (Task 3): `describeWorkspaceContract(name, factory)` is run over both `'worktree'` and `'stub'`, plus a source assertion that `registry.ts` is the only module naming either factory. The instant a future phase reintroduces the singular assumption — a direct import of the worktree factory, or a branch on backend id — one of those two goes red.
</assumption_delta_decision>

Its storage is an in-memory map; its `exec` runs the child through the same `run` function the worktree backend uses, with the same `buildChildEnv` and the same per-run scratch HOME, in a temp working directory it owns; `destroy` disposes its state and its scratch directory; `list` reports the workspaces it currently holds.     **The stub's root is a real directory on disk, created with `mkdtemp` under the OS temp directory with an `adl-stub-` prefix — not a synthetic in-memory path.** This is a correctness requirement, not a convenience. `assertWithinRoot` defeats symlink escape by calling `fs.realpath` on the nearest *existing* filesystem ancestor of the resolved candidate (Task 1). Given a root that has no filesystem existence, that walk climbs past the intended boundary to some unrelated real ancestor — the OS temp directory, or the drive root — and the containment test silently stops testing containment. The contract suite's `write` outside the root rejects case must pass for the same reason on both backends; with a synthetic root it would pass on the stub for no reason at all, which is the worst outcome available, because the suite would look like it was proving the guard while proving nothing.

Nothing is written to that directory — it exists so the guard has real ground to stand on — and `destroy` removes it alongside the scratch directory. State this rationale in a comment at the root's creation, naming the realpath dependency, because a future contributor optimising away "an empty directory nobody writes to" would silently disarm half the contract suite. The alternative considered and rejected: a second, purely lexical variant of the guard for the stub to use. That splits the guard into two implementations whose behaviour must be argued rather than observed to be identical — the same drift argument that makes Task 1 reuse `isRepoRelativePath` instead of writing a second path check.

    Implement `snapshot()` for real on both backends. On the worktree backend, capture with `git stash create`, which produces a commit object without disturbing the working tree; the returned `RestoreHandle` carries that sha as its `id`, `restore()` applies it, and `release()` drops the ref so the object becomes collectable. Untracked files are not captured by that mechanism, so `snapshot()` throws a `WorkspaceError` naming the untracked paths rather than returning a handle that silently captures a partial state — a restore that quietly loses files is worse than a refusal. On the stub backend, the handle holds a copy of the in-memory map, `restore()` swaps it back, and `release()` drops the copy.
