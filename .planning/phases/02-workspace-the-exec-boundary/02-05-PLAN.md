<objective>
Make the credential boundary and the disposable HOME true by construction: every child starts from an explicitly built environment, credentials reach exactly the one call that named them, and everything the agent writes as configuration dies with a directory that stops existing.

**MVP user story** (from ROADMAP.md § Phase 2 success criteria 4 and 5): **As a** maintainer who has handed ADL my forge token and my model API keys, **I want to** see that a child process ADL launches cannot read either of them out of its environment, **so that** installing a daemon with repository write access is a decision I can defend in a security review.

Purpose: `02-RESEARCH.md § Pitfall 6` reproduced the trap this plan must not fall into — on Windows, Node injects eleven variables into a child given an empty env, so an emptiness assertion is red on the maintainer's own machine and invites someone to "fix" it into an assertion that proves nothing. D-11's phrasing is already correct and must not be tightened. `§ Pitfall 10` and `§ Pitfall 11` supply the two subtler failures: git configuration injected through the environment, and Windows keeping only one of two case-colliding keys.

Output: the completed env builder, the hardened scratch-HOME lifecycle, and the real-child assertion that tests the boundary the child actually sees rather than the code path that built it.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| manager credentials → child environment | The manager holds forge tokens and model API keys. `exec()`'s environment is the only place a credential can cross into agent-controlled territory, and once it is in a child's environment the agent can print it. |
| agent-written configuration → host | A child writing `~/.gitconfig` or `~/.npmrc` is writing to whatever `HOME` points at. If that is the host user's home, a hostile registry or a hook path persists after the run. |
| environment variables → git and npm behaviour | Several environment variables are not data but executable configuration: they name programs git and npm will run. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-2-16 | Information Disclosure | agent reads a forge token or model key out of its own environment and exfiltrates it in ordinary output | high | mitigate | D-10 zero-inherit default plus D-09 per-call allowlist, both in `buildChildEnv`; Task 3's real-child assertion measures the boundary the child sees rather than the object the builder returned. |
| T-2-17 | Tampering | agent writes an `.npmrc` naming a hostile registry, poisoning later installs on the host | high | mitigate | `npm_config_userconfig` and `npm_config_cache` pointed inside the scratch directory (reproduced working), plus D-07's fresh directory per run; Task 3 asserts neither file exists after teardown. |
| T-2-18 | Elevation of Privilege | `GIT_CONFIG_COUNT` with numbered key and value variables reaches a child through a widened allowlist, giving arbitrary git configuration and therefore arbitrary code execution | high | mitigate | Zero-inherit makes the vector unreachable today; a named hazard comment at the builder forbids prefix pass-through; recorded as a `must_haves.prohibitions` item so a later phase's verifier flags a reintroduction. |
| T-2-19 | Information Disclosure | a credential value is echoed in an error message, a log line, or a test snapshot | high | mitigate | Errors name the variable and never the value; the credential test uses unique sentinel values so an accidental echo is greppable; recorded as a prohibition. |
