<objective>
Make success criterion 2 true: *"Maintainer runs `adl logs -f` on a running feature, watches the
agent's transcript stream live, and can reconnect mid-stream without losing or duplicating output."*

Purpose: the tracer serves what is already on disk. The half that criterion 2 actually turns on —
following a file that is still being written, and resuming at exactly the right byte after the
connection drops — is the part with the real failure modes, and `04-RESEARCH.md`'s Assumption A2
flags filesystem-watch behaviour as differing enough across platforms that a missed append could
make the stream stall silently rather than lose or duplicate data. A stall is the worst of the three
outcomes because it looks like an idle agent.
Output: a follow loop with three distinguishable wire states, a client that resumes from its own
consumed offset, and a kill-and-reattach test that proves it.
</objective>

## Flagged assumption — OBS-02 edge probe row (unresolved)

The spec-less edge probe classified OBS-02 (*"Maintainer can follow a running agent's transcript
live"*) as **`unclassified`**; its guidance is "review manually". An `unclassified` row is never
auto-resolved with a backstop marker, so it stays `unresolved` and is surfaced here rather than
silently dropped.

**The specific ambiguity a reviewer should rule on:** OBS-02 says the maintainer can follow a
*running* agent's transcript *live*. Nothing in REQUIREMENTS.md or CONTEXT.md bounds any of the
three words:

- **How live is live?** No latency budget is stated anywhere. This plan's answer is that an event is
  visible to a follower within the follow loop's poll interval of being appended, and that the
  interval is a named constant rather than an incidental one — but no requirement fixes a number, so
  a reviewer who wants a bound should say so.
- **What happens when the agent is not running?** This plan's answer is that following a completed
  stage returns the whole transcript and then ends with a terminal wire state, and that following a
  stage that has not started returns the not-yet-created state rather than an error. Both are
  implementation answers.
- **How many followers may one transcript have?** This plan's answer is any number, because each is
  an independent read at its own offset and the store has one writer. Untested beyond two
  concurrent readers, and stated so the limit is visible rather than assumed absent.

Recorded as an assumption, not a decision. The first half is carried into this plan's poll-interval
constant and the second into the three-wire-state assertions.
</flagged_assumptions>

    Write these as failing tests first.

    - A request with `follow` absent returns everything from the given offset and ends the response — it does not hang waiting for more.
    - A request with `follow` set stays open, and a record appended after the request began arrives on the open stream.
    - A follow request against a transcript file that does not exist yet stays open and begins delivering records once the file appears — a follower attaching before the first event is ordinary.

    - When the attempt reaches a terminal state, the stream emits the ended event after delivering the final records and then closes — a client is never left guessing whether the agent is thinking or finished.
    - An offset that is negative, fractional, or non-numeric responds 400 and reads no file.
    - An offset past the current end responds without error, reporting the current length rather than an empty success.
    - Aborting the client connection stops the loop — no timer and no file handle outlives the request.
    - Two clients following the same transcript at different offsets each receive their own correct records.

  <action>
    Turn the tracer's history-only route into a real follow stream.

    **The loop.** After serving history from the requested offset, if follow was requested, poll the
    store at a named interval — export `TRANSCRIPT_POLL_INTERVAL_MS` rather than burying a number —
    reading from the last offset each time and emitting whatever whole records appeared. Poll rather
    than rely solely on a filesystem watcher: `04-RESEARCH.md`'s Assumption A2 records that watch
    behaviour differs enough across platforms that a missed notification is plausible, and the
    failure it produces is a silently stalled stream, which is indistinguishable from a slow agent
    and therefore worse than either losing or duplicating data. A watcher may be used as a latency
    optimisation on top of the poll, but the poll is what makes progress guaranteed; if you add one,
    say in a comment that it is an accelerator and not the mechanism.

    **The three states, on the wire.** `readTranscriptFrom` already returns three outcomes; map them
    one-to-one onto named stream events so a client can branch deterministically rather than
    inferring from an empty payload. Add a fourth for termination. The distinction is the substance
    of prohibition P4 in this plan's `must_haves`: a transcript that is still growing must be
    distinguishable on the wire from one that is complete, because a reader who cannot tell will
    treat a partial transcript as the agent's whole reasoning. Determine termination from the
    attempt's own recorded end rather than from the file having stopped growing — a quiet agent and
    a finished one look identical on disk.

    **Resumption data.** Every records event carries the offset to resume from. That value is the
    store's returned next offset, which excludes any partial trailing line — so a client that
    reconnects with it receives the completing record exactly once. Do not send a record index or a
    sequence number as the resume key; `ARCHITECTURE.md` §9 fixes the address as a byte offset, and a
    second addressing scheme would break the property that the CLI and a future dashboard are the
    same code.

    **Validation and lifetime.** Validate `offset` and `follow` per-route with the same validator
    convention the control routes use, responding 400 for a negative, fractional, or non-numeric
    offset before any read. Register an abort handler that clears the timer and closes any watcher,
    and assert it in a test — a follow route that leaks a timer per disconnected client is a daemon
    that degrades over a long session rather than failing visibly.

    **No curation.** D-07 is explicit that the full event detail reaches both the file and the live
    view verbatim, with no filtering layer in this phase. Do not add a level filter, a kind filter,
    or a default that hides thinking deltas. If the store needs a small addition to support the loop
    — a length probe that distinguishes absent from empty, say — add it there rather than
    reimplementing offset arithmetic in the route; two places that compute offsets is how a writer
    and a reader drift apart.
  </action>

    - When the stream drops mid-way, the command reconnects with the offset it last consumed, and the combined output contains every event exactly once — asserted by comparing against the transcript file's own contents.

  <action>
    Make `adl logs` a resumable follower.

    **`http-client.ts`.** Extend `streamStageLogs` to take an offset and a follow flag and to expose
    the stream as an async iterable of parsed events, using the server-sent-event parser installed in
    `04-01` against the existing bearer-header request wrapper. Never a second fetch call site and
    never a second auth mechanism — the CLI speaks HTTP through this one client, and that is what
    keeps it structurally unable to reach past the API.

    **`commands/logs.ts`.** Follow `pause.ts`'s `(options, deps)` shape with the client and the write
    sink injected, so the whole reconnect behaviour is testable without a real daemon or a real
    socket. Track the resume offset as *what this client has written*, not what it has received: on
    each records event, write the events first and only then advance the tracked offset. A client
    that advances on receipt and then dies before writing has silently dropped output on its next
    reconnect, and the loss would be invisible because the offsets line up perfectly.

    Reconnect on a dropped stream by reissuing the request with the tracked offset. Bound it: count
    consecutive failures, stop after a stated maximum, and report why. An unbounded retry against a
    daemon that has been stopped is a command that never returns, and the user's only recourse is a
    signal.

    Branch on the four wire states rather than inferring: keep waiting on nothing-new, keep waiting
    on not-yet-created, exit 0 on ended. Write events as they arrive rather than accumulating —
    accumulate-then-flush would reproduce, at the client, exactly the buffering anti-pattern the
    store was built to avoid at the writer.

    Surface a connection failure as the existing daemon-unreachable error so the message a user sees
    is the same one every other verb produces. Register `--follow`/`-f` and `--offset` in
    `index.ts` inside the existing verb wrapper.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| any authenticated API client → transcript contents | A follower reads everything an agent produced, including whatever it echoed |
| client-supplied offset → filesystem read | The resume offset arrives from a query string on every reconnect |
| an abandoned connection → daemon resources | A follower that vanishes leaves a loop the server started |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-4-30 | Denial of Service | unvalidated offset on the follow route | high | mitigate | The route validates `offset` as a non-negative integer per-request and responds 400 before any read, and the store refuses an invalid offset independently — two independent refusals, so a future route that forgets is still covered. ASVS V5 |
