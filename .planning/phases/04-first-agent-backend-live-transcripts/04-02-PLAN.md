<objective>
Close `D-2-08-1`, the defect `.planning/STATE.md` carried forward into this phase: on a provisioned
Linux deployment the agent cannot run git inside its own worktree — `fatal: detected dubious
ownership in repository`, exit 128.

Purpose: success criterion 1 of this phase is *"a developer agent … makes a real commit inside a
feature worktree"*. This defect blocks that criterion on exactly the platform CI runs it on, and it
is a workspace-layer bug that happens to only manifest when an agent tries to commit — so it is
fixed here, beside the adapter rather than inside it.
Output: a scratch-HOME `.gitconfig` written at workspace-creation time, and a test that proves the
exec path can run git inside the worktree.
</objective>

  <action>
    **Where the fix belongs, and where it emphatically does not.** `env.ts` already points every
    child's `GIT_CONFIG_GLOBAL` at `<scratchHome>/.gitconfig` — a file `createScratchHome()` never
    writes, because it only creates the directory. Git reads `safe.directory` from system and global
    configuration only, never from a repository's own config, and `GIT_CONFIG_NOSYSTEM` is already
    set — so that scratch global file is the single channel through which this can be set at all.
    The fix is therefore a direct file write inside `@adl/workspace`. It must **not** be attempted
    through `ExecSpec.env`: `namesGitExecution()` refuses the git-configuration family there by
    design (WR-02), and routing around that refusal would reopen the arbitrary-config-is-arbitrary-
    execution vector that whole control exists to close.

    **`src/exec/scratch-home.ts`.** Export `SCRATCH_GITCONFIG_FILENAME` as the `.gitconfig`
    basename and have `env.ts`'s `neutralisers()` build its `GIT_CONFIG_GLOBAL` value from that same
    constant, so the writer and the pointer cannot drift apart. Export
    `writeScratchGitConfig(home, { safeDirectories })`, which writes a git-config file containing a
    `safe` section with one `directory` entry per supplied path, using the `writeFile(..., { encoding: 'utf8', mode })`
    convention `recordOwner` already establishes — but with a mode that permits the dropped worker
    identity to read **and write** the file, not `recordOwner`'s `0o600`. Two reasons the mode
    differs and both matter: `env.ts`'s own comment says the agent may write to this file and it
    dies with the directory, and the worker runs under a different identity than the daemon that
    creates it. Use a plain write rather than `flag: 'wx'` — unlike the owner marker, an existing
    file here is a rewrite, not an anomaly, and duplicated entries would accumulate.

    Follow this module's established discipline in two respects. Paths are written verbatim as
    given; git compares `safe.directory` values literally, so the caller supplies the exact strings
    git will report, and the writer does not normalise, resolve, or case-fold them. And a failure to
    write is a real failure here rather than a swallowed one — unlike `recordOwner`, whose failure
    costs one uncollectable directory, a missing config file means every git command the agent runs
    fails, so let the error propagate as a `WorkspaceError` naming the home path and the OS error
    code (never a value out of any child's environment).

    **`src/worktree/backend.ts`.** Call `writeScratchGitConfig` in `worktreeWorkspace()` immediately
    after `createScratchHome()` returns and **before** `applyWorkerAccess` runs, passing both
    `worktreePath` and `spec.mainRepo` as safe directories. Both are needed: a linked worktree's git
    operations reach into the main repository's `.git`, so marking only the worktree leaves the
    other half of every command unowned. Ordering is load-bearing twice over — the file must exist
    before any child is launched, and creating it before the access grant means the same grant that
    covers the directory can cover the file. Read `privilege.ts` first: if `applyWorkerAccess` grants
    only the directories it is given and not the files inside them, add the config file's path to
    the granted list explicitly rather than assuming recursion.

    Add a comment at the call site recording what this fixes and why it is here rather than in the
    adapter: `D-2-08-1`, `fatal: detected dubious ownership in repository`, exit 128, git ≥2.35.2's
    CVE-2022-24765 mitigation refusing to operate in a repository owned by a different uid than the
    current process. Also record Assumption A4 honestly: this marking makes git proceed, and it is
    **not** a substitute for the worktree's on-disk ownership being right. If the underlying cause on
    a given deployment turns out to be a real worker-uid/worktree-owner mismatch, that is a WORK-05
    concern this marking would mask — say so in the comment so a future reader is not misled into
    thinking ownership was verified.

    **`src/index.ts`.** Export `writeScratchGitConfig` and `SCRATCH_GITCONFIG_FILENAME` with a "why
    public" comment in the barrel's established style: an out-of-tree workspace backend that stands
    up its own scratch home faces the identical problem and must be able to solve it with the same
    code rather than an unreviewed second implementation — the same argument that already justifies
    exporting `applyWorkerAccess`.

    **`test/worktree/safe-directory.test.ts`** runs the behaviour list. For the end-to-end case,
    build a real worktree workspace over a temp git repository and drive `git status --porcelain`
    through `workspace.exec`, asserting exit code 0. On a host where no privilege drop occurs the
    test still proves the config file is present and read — assert the exec succeeds and,
    separately, that `git config --get-all safe.directory` run through the same exec path reports
    both paths, which is the observable form of "the file is on the child's global config path".
    Use this package's existing platform gate for any POSIX-only mode assertion so a Windows skip is
    visible with a stated reason rather than silent.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the agent's child process → git configuration | Git configuration names programs git executes, so anything that can write git config can execute code |
| the dropped worker identity → the scratch HOME's files | The worker is a different, less-privileged OS identity than the daemon that created the directory |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-4-05 | Elevation of Privilege | the scratch `.gitconfig` becoming a general config channel | high | mitigate | The writer takes only a list of directory paths and emits only a `safe` section — it accepts no arbitrary key or value, so no caller can reach `core.hooksPath`, `core.pager`, or an `sshCommand` through it. `ExecSpec.env`'s refusal of the git-configuration family is untouched, and a test asserts that refusal still fires |
| T-4-06 | Tampering | the agent rewriting the file to widen its own safe set | low | accept | The agent already runs inside a directory it controls, and `env.ts` documents that it may write to this file; widening `safe.directory` inside a home that dies with the run grants the agent nothing it does not already have. Accepted rather than mitigated because the alternative — a read-only global config — breaks the documented ability of the agent to set its own git identity |
| T-4-05b | Spoofing | a `safe.directory` entry naming a path the workspace does not own | medium | mitigate | The call site supplies exactly two values, both derived from the workspace's own `WorkspaceSpec` (`worktreePath`, `spec.mainRepo`) — never from an `ExecSpec`, a config file, or any agent-supplied string. A test asserts the file contains those two entries and no others |
</threat_model>
