<objective>
Lift the two prerequisites out of the tracer that would otherwise make it a plan about plumbing
rather than about the agent: the `assign` message a worker needs in order to create its own
workspace, and the round/attempt rows the transcript path and the spend ledger join on.

Purpose: `dispatcher.ts` currently sends a worker a `workspaceHandle` and nothing else, with a
comment saying actual worktree creation is a later plan's job — this is that plan. Separately,
`rounds` and `stage_attempts` exist in the schema since Phase 1 and have never had a writer; the
transcript file path (`logs/<feature>/<round>/<stage>/<attempt>.ndjson`) and `usage_events`'
`round_id`/`stage_attempt_id` columns both address through them, so both would be synthesised
without this.
Output: an `assign` message that is sufficient on its own, and one place that opens and closes a
stage attempt.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| manager → forked worker (`assign`) | The message is the worker's whole world; anything it does not carry, the worker either guesses or cannot do |
| untrusted HTTP path parameter → a filesystem path | An attempt id arriving from a request must not become a path component without passing through the database |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-4-14 | Tampering | an `assign` carrying an attacker-chosen `mainRepo` or `scratchRoot` | high | mitigate | Both values are populated by the dispatcher from the daemon's own configuration and never from a request, a config file the agent can write, or a feature row. `parseManagerMessage` validates every field at the worker's receiving end, and `workspaceBackendId` is constrained to the registered ids rather than accepted as a free string |
| T-4-15 | Information Disclosure | an attempt id from a request becoming a filesystem path | high | mitigate | `findAttempt` is the only sanctioned resolution and returns a record assembled from database columns rather than from the supplied string; `04-08`'s route is required to build its path from that record. A test asserts an unknown id resolves to `undefined` rather than to a plausible path |
| T-4-16 | Repudiation | a repair reprompt overwriting the attempt it retried | medium | mitigate | `openAttempt` increments the attempt ordinal rather than reusing it, so D-13's second attempt is a second row visible in history. A test asserts two `openAttempt` calls produce attempts 1 and 2 |
| T-4-17 | Denial of Service | two concurrent dispatches both claiming round number 1 | medium | mitigate | Round selection and attempt insertion happen in one transaction against the same connection the manager is the sole writer on, and a test drives two concurrent `openAttempt` calls and asserts they do not both claim the same round number |
</threat_model>
