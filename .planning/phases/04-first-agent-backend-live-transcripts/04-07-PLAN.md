<objective>
Make success criterion 3 true: *"The backend's CLI version is pinned and preflight-checked at
startup, so an unexpected version is reported as a broken installation rather than discovered
mid-run."*

Purpose: D-01 pins the version exactly and D-02 makes a mismatch hard-block dispatch, and both were
chosen against the alternative — warn and continue — because an unattended loop running against an
untested CLI version is precisely the silent risk this project exists to avoid.
`04-RESEARCH.md` § Pitfall 2 adds the complication that the version output's format is not a
contracted API surface, which is why the parser is held to a recorded fixture rather than to a
regex written from memory.
Output: a probe on the backend, a startup gate in the manager, and a refusal a human can act on.
</objective>

    Create `packages/agent-claude-code/src/preflight.ts`.

    **`parseClaudeVersion(stdout)`** finds a version-shaped token in the output and returns it, or
    returns undefined. Parse defensively: `04-RESEARCH.md` § Pitfall 2 establishes that the version
    output's exact shape is not documented anywhere, so an exact whole-string comparison is a
    regression waiting for the first cosmetic change to the line. Match a version-shaped token rather
    than the whole line, and pin the parser's test against
    `test/fixtures/claude-version.txt` — the real recorded output from `04-01` — so the test fails
    the day the pin moves and the fixture is not re-captured. State in the docblock that
    re-pinning obliges re-running that capture, and that this file is where a future maintainer will
    find out why.

    **`preflightClaudeCode(deps)`** takes an injected version-check runner returning stdout and an
    exit code, and returns a `PreflightResult` — never throws. Follow the classification discipline
    `stage-error.ts` sets: an expected-but-notable outcome is a named value, and only a programmer
    error is an exception. Distinguish at least three not-ok kinds and reuse the existing stage-error
    vocabulary where it already has a name for the condition: the binary could not be run at all, the
    binary ran but its output carried no readable version, and the binary reported a version that is
    not the pinned one. Three, not one boolean, because they lead an operator to three different
    actions — install it, investigate it, or change the installed version — and collapsing them
    hides which.

    The detail string names the expected version and what was found, and says the installation is
    broken. That wording is success criterion 3's own and `04-CONTEXT.md`'s specific ask; write it
    once here so every caller reports it identically rather than paraphrasing.

    The version check is still an external CLI invocation, so it goes through the same exec boundary
    as everything else — pass it in as an injected runner so this module stays free of any process
    dependency and the package's lack of one holds. Choose the ADL-owned exec owner rather than the
    agent-owned one and say why in a comment: this launch is ADL asking a question about its own
    installation, not an agent doing work on a feature's behalf.

    **`backend.ts`.** Replace the tracer's inline probe with a delegation to `preflightClaudeCode`,
    mapping its result onto the probe shape `04-03` defined. Do **not** call it from `run()`.
    `04-RESEARCH.md`'s anti-patterns are explicit: repeating the check on every invocation is wasted
    latency and does not match diagnosing a broken install *before* a feature is run through it. Add
    a comment at the top of `run()` recording that the check is a startup concern and naming the
    manager module that owns it, so a future contributor does not "fix" the apparent omission.

    Export the preflight surface from the package barrel with a "why public" comment: the manager's
    startup gate is the caller, and a later `adl doctor` will be the second.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the installed CLI binary → ADL's trust that it behaves as tested | Whatever is on PATH is what runs with the daemon's credentials |
| version-check output → ADL's decision to dispatch | The output is text from an external program and is parsed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-4-26 | Spoofing | an unexpected binary on PATH answering to the agent CLI's name | high | mitigate | The exact-pin comparison means any binary whose reported version is not the tested one hard-blocks dispatch — a substituted binary must both be present and report exactly the pinned version to get past the gate. Tests assert one patch above and one patch below both refuse |
| T-4-27 | Denial of Service | a version-check invocation that never returns | medium | mitigate | The check runs through the same exec boundary as every other launch, which carries a wall-clock bound; a check that does not complete is a refusal rather than a hung startup. The gate runs before the API binds, so a hang cannot leave a half-started daemon serving requests |
| T-4-28 | Repudiation | a mid-run version discovery blamed on the feature | high | mitigate | The gate runs once at startup before any lease is acquired, so a version problem is attributed to the installation rather than surfacing as a failed feature. A test asserts a queued feature is still queued after a refused start |
| T-4-29 | Tampering | version output crafted to satisfy the parser | low | accept | Anything that can place a binary on the daemon's PATH already has code execution as the daemon user; the version gate is an operational correctness control, not a security boundary, and treating it as one would imply a signature check this project has no key infrastructure for. Accepted and stated so it is not mistaken for a defence it is not |
</threat_model>
