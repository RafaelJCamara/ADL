## Flagged assumption — BACK-01 edge probe row (unresolved)

The spec-less edge probe classified BACK-01 (*"ADL drives agentic CLIs that own their own loop and
tools, through an `AgentBackend` port"*) as **`unclassified`**; its guidance is "review manually".
Per protocol an `unclassified` row is never auto-resolved with a backstop marker, so it stays
`unresolved` and is surfaced here rather than silently dropped.

**The specific ambiguity a reviewer should rule on:** BACK-01 says ADL drives agentic CLIs *that own
their own loop and tools*. Nothing in REQUIREMENTS.md or CONTEXT.md states what the port promises at
the two boundaries of that ownership:

- **What happens when the delegated loop does something ADL did not ask for** — writes outside the
  worktree, installs a package, opens a network connection. This phase's answer is that the port
  says nothing about it, because containment is the workspace's job (WORK-02, and Phase 15's
  WORK-08 for write auditing). That is an architectural answer, not a stated requirement, and it
  means `AgentCapabilities` deliberately does not carry a tool allowlist in this phase.
- **Whether the port must be able to represent a loop ADL owns** — Phase 11's `ModelBackend` family.
  This phase's answer is that `AgentEvent` and `AgentTask` are written so an owned loop could emit
  the same events, but no owned-loop adapter exists to falsify that. The claim is unproven until
  Phase 11 builds the second family, and the honest statement is that this interface has exactly
  one implementation and is therefore unfalsifiable today — which is precisely why the ROADMAP
  makes Phase 11 the sole breadth item permitted before the dogfood gate.

Recorded as an assumption, not a decision. It is carried into `04-09`'s prohibition P3, whose
assertion — that the port's vocabulary names no vendor-specific concept — is the observable form of
the second half.

  <context>
    This is a one-way door. The transcript file is an on-disk format that outlives the run: Phase 9
    reads it to build the pull-request rollup, Phase 17's dashboard streams it, and every transcript
    already written by every adopter is in whatever shape is chosen here. Changing it later is not a
    refactor — it is a migration over other people's files, or an accepted permanent split between
    old-format and new-format transcripts.

    Two forces pull in opposite directions. `PITFALLS.md` Pitfall 7 and D-07 both argue for keeping
    everything, because a summarisation step in Phase 9 working from an already-lossy stream cannot
    recover what was dropped. `ARCHITECTURE.md` §4's "the adapter is the only thing that has seen
    the CLI's raw shape" argues the opposite way: if the raw line survives into the file, every
    downstream reader gains the *ability* to parse it, and Hyrum's Law says one of them eventually
    will — at which point the vendor-neutrality claim has a second, undocumented leak.

    Byte-offset addressing (§9) constrains all three options equally: whatever is chosen, one record
    is one line, records are append-only, and the offset is a byte count.
  </context>
  <options>
    <option id="option-a">
      <name>The translated ADL event only, in a stable envelope</name>
      <pros>One format, one vocabulary. Every downstream reader — Phase 9's rollup, Phase 17's
      dashboard, a third party — sees the same events regardless of which backend produced them,
      which is the vendor-neutrality claim made literal in the artefact rather than only in the
      code. The file is smaller, and there is no second shape for a reader to become dependent
      on.</pros>
      <cons>Anything the backend emitted that the translator did not model is gone, permanently and
      silently. If a future Claude Code release adds an event kind, transcripts captured before the
      translator learns it have lost it. Debugging an adapter bug from a transcript becomes
      impossible, because the evidence is the translator's output rather than its input.</cons>
    </option>
    <option id="option-b">
      <name>The backend's raw line only; translation happens at read time</name>
      <pros>Nothing is ever lost, and an adapter bug is diagnosable from a stored transcript because
      the input survives. A translator improvement retroactively improves every stored
      transcript.</pros>
      <cons>The file is backend-specific, so every reader must know which backend wrote it and hold
      a translator for each — exactly the `if (backend === 'x')` shape Phase 11's lint rule exists to
      ban, pushed out of the code and into the data. A mixed-backend project has transcripts in as
      many formats as it has backends.</cons>
    </option>
    <option id="option-c">
      <name>The translated event, with the backend's raw line retained beside it in the same record</name>
      <pros>Loses nothing and stays readable by a backend-blind consumer: a reader that only knows
      ADL's vocabulary ignores the raw field entirely, and a debugger has the input. The envelope is
      one shape across backends, so the vendor-neutral reading path is the default path.</pros>
      <cons>Roughly doubles transcript size, on a file that grows with every token delta under
      `--include-partial-messages`. The raw field is a documented invitation for a downstream reader
      to depend on a backend's shape, which is the leak option-a avoids by construction — mitigating
      that needs a stated rule (and, later, a lint rule) rather than the format doing it.</cons>
    </option>

    backends fit by branching, and the branch will be invisible because the type names made it look

    **`AGENT_EVENT_KINDS`** — a frozen tuple of the eight kinds D-07 names, paired with the

    **`AgentEventSchema`** — a Zod discriminated union on `kind`, one `.strictObject` per kind with a
    stable `.meta({ id })`, types via `z.infer`. Carry what each kind genuinely needs and nothing
    more: `started` names the model and the backend-declared capabilities in force; `text` and
    `thinking` carry an incremental delta plus enough identity to reassemble a message; `tool_call`
    carries a call id, a tool name, and its input; `tool_result` carries the matching call id, the
    result, and whether it errored; `usage` carries token counts as four separately nullable numbers
    — never defaulted to zero, because Phase 1's D-31 made "the backend did not report this" and
    "the backend reported zero" two facts that cannot be recovered once merged; `result` carries the
    terminal outcome, the wall-clock duration, and an optional backend-reported cost; `error` carries
    a `StageErrorKind` from the existing union plus a message. Reuse `StageErrorKind` rather than
    inventing a second failure taxonomy — D-12's classification is already the vocabulary the loop
    acts on.

    **`AgentTaskSchema`** — what ADL hands the backend for one invocation: the rendered system
    prompt and the rendered instructions as two separate already-built strings (the port never
    receives a spec or a template, because `PromptBuilder` owns rendering and adapters never build
    prompts — `ARCHITECTURE.md` §4), the workspace-relative context files to load explicitly, and a
    `limits` block carrying a wall-clock bound and a turn bound. Do not put a model name here if the
    backend owns model selection; do put one if ADL selects it — read `CAPTURE.md`'s record of what
    the CLI reports at `started` and choose the side that matches reality, stating which in the
    docblock.

    **`AgentCapabilitiesSchema`** — what a backend declares about itself so the loop can degrade
    honestly rather than assume: whether it emits incremental events at all, whether it reports
    usage, whether it reports cost, whether it can resume a session, whether it enforces a turn cap.
    This is the mechanism by which `04-10`'s cost recording and Phase 6's budget enforcement can say
    "this backend cannot report cost" instead of silently recording nothing. `04-RESEARCH.md`
    records that one CLI family returns a single JSON object at completion with no incremental
    stream at all, so "emits incremental events" is a real axis, not a hypothetical one.

    **`AgentRunner`** — the interface itself. Two methods. `run(task, ctx)` takes an `AgentTask` and
    a context carrying the `Workspace` the invocation runs inside, an event sink callback, and an
    `AbortSignal`, and resolves to an `AgentRunResult` naming the terminal outcome and the observed
    usage. `probe()` resolves to an `AgentProbe` reporting whether the backend is usable and, when
    it is not, why — installed version, expected version, and a human-readable detail. Both return
    rather than throw for expected-but-notable outcomes, following `StageError` and
    `compareAndSwapState`: a missing binary, an auth failure, and a version mismatch are all answers,
    not exceptions. Write the docblock for `run` to state plainly that the runner **translates and
    never re-drives** — an implementation that branches on a `tool_call` event to make a decision has
    misunderstood the delegated-loop family, and the events exist to be logged and reported, not
    consumed as control flow.

    byte-offset addressing depends on and that later phases will rely on: one record is one line,
    and the file is append-only. State that the sequence number exists for ordering and gap
    detection, and that it is deliberately **not** the addressing scheme — `ARCHITECTURE.md` §9 fixes
    the address as a byte offset, and a second scheme would break the property that the CLI and the
    dashboard are the same code.
