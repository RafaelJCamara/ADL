<objective>
Build the transcript store: the deterministic path a stage attempt's NDJSON file lives at, and the
byte-offset append-and-read primitive that makes `adl logs -f`'s reconnect contract possible.

Purpose: `ARCHITECTURE.md` §4 fixes transcripts as NDJSON files and says plainly they never go in
database rows; §9 fixes the addressing as a byte offset, because that is what lets the CLI and a
future dashboard be the same code. Both the writer (the worker, appending as events arrive) and the
reader (the manager, serving `?offset=N&follow=1`) depend on one shared understanding of where the
file is and what an offset means — so it is one module, built and tested before anything streams
through it.
Output: a path builder that only accepts a resolved attempt address, and a store whose offsets are
byte counts a reader can trust.
</objective>

  <behavior>
    Write these as failing tests first.

    - `openTranscriptWriter` on a path whose parent directory does not exist creates the directory chain and then the file.
    - `append` returns a strictly increasing offset, and the returned value equals the file's size on disk after the call.
    - Appending a record whose serialised form contains a multi-byte character advances the offset by the byte length, not the character count — asserted by comparing against the file's real size.
    - Every appended record occupies exactly one line: reading the file back and splitting on newline yields one parseable record per non-empty line.
    - `readTranscriptFrom(path, 0)` after three appends returns all three records and a next offset equal to the file size.
    - `readTranscriptFrom(path, offsetAfterTwo)` returns only the third record.
    - `readTranscriptFrom` at an offset equal to the current size returns a past-end outcome carrying the current length, not an error and not an empty read a caller could mistake for end-of-stream.
    - `readTranscriptFrom` on a file that does not exist returns an absent outcome, not a throw — a reader attaching before the first event is ordinary.
    - A read taken while a record is only partially written returns the whole records before it and a next offset at the start of the partial line, and a subsequent read after the record completes returns it exactly once.
    - A negative, non-integer, or non-finite offset is refused with a named error rather than passed to the filesystem.
    - Appended records are visible to a separate reader before the writer is closed.
  </behavior>
  <action>
    Create `packages/manager/src/store/ndjson-log-store.ts` — the append-and-read primitive both the
    worker and the HTTP route go through.

    **`openTranscriptWriter(path)`** creates the parent directory chain, opens the file for
    appending, and returns a small handle with `append(record)`, `offset()`, and `close()`. `append`
    serialises the `TranscriptRecord`, writes it followed by a newline, and returns the file's new
    byte length — which is precisely the offset a reader should ask for next. Track the offset by
    accumulating the byte length of what was written, using a byte-length measurement rather than a
    string length: a multi-byte character makes those two numbers diverge, and a reader resuming
    from a character count instead of a byte count reads from the middle of a character. That is a
    correctness requirement of the reconnect contract, not a style preference.

    Append as each record arrives. `04-RESEARCH.md`'s anti-patterns name buffering the whole
    transcript until the process exits as the thing that makes a live view impossible and loses
    everything on a mid-run crash — which is the exact failure mode this phase's success criterion 2
    is about.

    **`readTranscriptFrom(path, offset)`** returns a discriminated union rather than throwing,
    following `ScratchHomeTeardown`'s three-outcome discipline: `read` carrying the whole records
    found and the offset the next read should use; `absent` when the file does not exist yet, which
    happens whenever a reader attaches before the first event; and `past-end` carrying the current
    length when the offset is at or beyond it. Three named outcomes rather than an empty array,
    because a caller cannot distinguish "no new data yet" from "nothing will ever come" from an
    empty success — and `adl logs -f` has to.

    **Whole records only.** A reader may land mid-line while the writer is between the record and its
    newline. Read from the offset, split on the newline, and if the final segment has no terminating
    newline, do not emit it and do not count its bytes toward the returned next offset. The partial
    bytes are re-offered on the next read and emitted exactly once when the record completes. This
    single rule is what makes "reconnect without losing or duplicating output" true; without it a
    reconnect either drops a record or repeats one, and both are what success criterion 2 forbids.

    **`transcriptLength(path)`** returns the current byte length, or `undefined` when the file is
    absent. This is what the route needs to answer a `?offset=` far past the end without reading
    anything.

    Validate the offset before it reaches the filesystem: refuse a negative, non-integer, or
    non-finite value with a named error. `04-RESEARCH.md`'s ASVS V5 row is specifically about this
    parameter arriving from a query string, and a validation that lives in the store applies to every
    caller rather than only to the one route that remembered.

    Use the `codeOf(error)` narrowing helper's shape for filesystem error handling, and treat an
    absent file as an outcome rather than an exception. Do **not** implement following or watching
    here — this module answers "what is in the file from offset N", and `04-08` builds the follow
    loop on top of it. Keeping the two apart is what lets the offset semantics be tested exhaustively
    without a timer, and it isolates the platform-dependent watch behaviour Assumption A2 flags into
    one place.

    Export the surface from `packages/manager/src/index.ts` with a "why public" comment naming both
    consumers and stating that they must agree on offsets.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP query parameter → filesystem read offset | An offset arriving from a request is passed to a filesystem read |
| resolved attempt address → filesystem path | Path components originate as database values, which originate as feature and stage identifiers |
| agent output → transcript file content | Every byte in the file came from a model's output |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-4-18 | Information Disclosure | path traversal through an address component | high | mitigate | `transcriptPathFor` accepts only the resolved address type, refuses any component carrying a separator, parent reference, path root, or null byte, and applies the workspace package's own containment check against the logs root as a backstop. Tests assert refusal rather than sanitisation |
| T-4-19 | Denial of Service | an unvalidated offset reaching the filesystem | high | mitigate | The store refuses a negative, non-integer, or non-finite offset with a named error before any read is attempted, so the validation applies to every caller rather than to whichever route remembered. ASVS V5 |
| T-4-20 | Repudiation | a reconnect duplicating or dropping a record | high | mitigate | Whole-records-only reading plus a byte-counted next offset; a partial final line is neither emitted nor counted, and is emitted exactly once when it completes. A test drives the partial-line case directly |
| T-4-21 | Denial of Service | unbounded transcript growth on a long run | low | accept | A transcript grows with the run and is reclaimed with the feature; capping or rotating it would silently truncate the audit trail D-07 exists to preserve. Accepted for v1 and revisited with Phase 15's size-capping of agent output before it reaches a forge, which is the boundary where size actually matters |
</threat_model>
