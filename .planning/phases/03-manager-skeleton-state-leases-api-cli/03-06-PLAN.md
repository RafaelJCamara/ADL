<objective>
Give the daemon a lifecycle: a config file that is the operator's trust anchor, a startup gate that
refuses to corrupt a database it does not own, a deterministic clean slate at boot, and a shutdown
that stops rather than abandons.

Purpose: ROADMAP criterion 4 is literally about surviving a restart, and D-37's schema gate protects
databases ADL does not own. Both are cheapest to get right before anyone has installed it — a
released daemon that opens a newer schema optimistically cannot be fixed retroactively for a
database it already corrupted.
Output: `loadDaemonConfig`, the startup gate, the boot orphan kill, and graceful shutdown.
</objective>

## Flagged assumptions — EXEC-01 and EXEC-06 edge-probe rows (unresolved)

Both were classified **`unclassified`** by the spec-less edge probe and are therefore surfaced rather
than auto-resolved. A reviewer should rule on each.

**EXEC-01** — *"Manager process owns detection, queue, state, config, credentials, and accounting."*
The unstated boundary is **what happens when two manager processes are started against the same
database**. Nothing in REQUIREMENTS.md or CONTEXT.md forbids it, and SQLite will happily let both
open the file. This plan does **not** add a PID file, an advisory lock, or a single-instance check —
the lease fence limits the damage (two managers cannot both lease the same feature) but they would
both reap, both dispatch, and both kill orphans at boot, and the second one's boot orphan kill would
target the first one's live workers. Recorded as an unresolved assumption; a single-instance guard
would be a small, additive change if a reviewer wants one.

**EXEC-06** — *"Feature state, rounds, spend, and transcripts survive daemon restart."* The unstated
boundary is **transcripts**, which do not exist yet — Phase 4 owns them (OBS-02), and this phase's
`03-CONTEXT.md` puts live transcript streaming explicitly out of scope. This plan therefore proves
survival for state, rounds, and spend only, and treats the transcript clause as satisfied by
construction because there is nothing to lose. That reading is an assumption. If a reviewer expects
EXEC-06 to be provable only once transcripts exist, this requirement is partially deferred to Phase 4
and should be recorded as such rather than checked off here.
</flagged_assumptions>

  <decision>
    D-37 is already locked: refuse a schema newer than the daemon, copy the database file before
    auto-migrating an older one. That is not being re-asked. What is not yet decided is **where the
    daemon's own schema version number comes from, where the pre-migration copy goes, and what
    happens to that copy afterwards.**
  </decision>
  <context>
    D-37 is rated **one-way**, and uniquely so: it is the only decision in this phase that protects
    data ADL does not own. Every other one-way property here can be relaxed or migrated. This one
    cannot — once a version of the daemon exists in the wild that opens a newer schema optimistically,
    no later fix repairs a database it already corrupted, and ADL is explicitly installed into other
    teams' repositories.

    The database currently has **no** `schema_version` row at all: migration `0001` creates the `meta`
    table and seeds nothing (verified). So this startup path is also the first writer of that value,
    and whatever it writes becomes the number every future daemon compares against.
  </context>
  <options>
    <option id="option-a">
      <name>Version = the highest applied migration name; copy beside the database, kept forever</name>
      <pros>The daemon's expected version is derived from what is actually in `packages/db/migrations/`,
      so it cannot drift from the code. The copy lands as `adl.db.pre-<version>-<timestamp>` in the
      same directory, which is where an operator looks first and which needs no new configuration
      key. Keeping every copy means a bad upgrade three versions ago is still recoverable.</pros>
      <cons>Copies accumulate silently in the operator's directory with no pruning, and a large
      database makes that real disk. WAL sidecar files must be checkpointed before the copy or the
      snapshot is incomplete.</cons>
    </option>
    <option id="option-b">
      <name>Version = a hand-maintained constant in the daemon source; copy beside the database, most recent N kept</name>
      <pros>The constant is a deliberate, reviewable act — bumping it is a decision someone makes,
      not a side effect of adding a file. Pruning to the most recent few copies bounds the disk cost.</pros>
      <cons>A hand-maintained constant can drift from the migrations directory, and the failure mode
      of that drift is precisely the one D-37 exists to prevent. Pruning is a delete path in the
      startup sequence — the one place a bug is most expensive.</cons>
    </option>
    <option id="option-c">
      <name>Version derived from migrations; copy required but its destination is an operator config key with no default</name>
      <pros>The operator explicitly chooses where their backup goes, which suits a database ADL does
      not own, and ADL never writes to a directory the operator did not name. Makes the backup a
      visible part of installation rather than a surprise file.</pros>
      <cons>First run fails until the key is set, and an operator who sets it to a path that later
      becomes unwritable gets a refusal to start on the day they most want the daemon up. Adds a
      required config key to the install story that Phase 18 will want to remove.</cons>
    </option>
  </options>
  <acceptance_criteria>
    - A choice is recorded in the resume signal, and the selected option's version source, copy destination, and retention behaviour are what Task 3 implements.
    - Regardless of option: the daemon refuses a newer schema and writes nothing in that case, and the copy completes before the first migration statement runs.
  </acceptance_criteria>
  <resume-signal>Select: option-a, option-b, or option-c — and name a retention count or a path if the option needs one.</resume-signal>

  <behavior>
    - Against a database whose `schema_version` is greater than the daemon's, `runStartupGate` returns a refusal naming both versions, and the database file's bytes are unchanged afterwards.
    - Against a database whose `schema_version` is absent (a fresh, migrated-but-unseeded database), the gate migrates, seeds `schema_version`, and proceeds.
    - Against a database whose `schema_version` is older, the gate produces the pre-migration copy first and only then migrates; the copy's bytes equal the original's bytes as they were before migration.

    - After a successful gate, every repository declared in `repos` exists in the `repos` table with the declared values.
    - A repository present in the table but absent from the config is left in place and logged, not deleted.
    - Re-running the gate against an already-current database is a no-op that writes no new copy.
  </behavior>
  <action>
    Implement `feature-state.ts`'s versioning rule 2 in full, in the order D-37 fixes: schema gate,
    copy-and-migrate, repository reconciliation, then (Task 4) lease expiry and orphan kill, then
    dispatch.

    **`src/boot/startup.ts`.** Export `DAEMON_SCHEMA_VERSION` sourced per the option selected in
    Task 1, `StartupGateResult` as a discriminated union (proceed, or refuse carrying a typed reason),
    `SchemaVersionRefusal`, `runStartupGate(deps)`, and `reconcileRepos(deps)`.

    The gate's first act is reading `meta.schema_version` through `metaRepository` — before any other
    database access. If it is greater than the daemon's, refuse: return the refusal, write nothing,
    and let the caller exit non-zero with a message naming the stored version, the daemon's version,
    and what to upgrade. A daemon that opens a newer schema optimistically is the exact failure rule 2
    was written to prevent, and it is unrecoverable for the adopter. If it is not an integer, refuse
    for the same reason — `03-02`'s three-way `getSchemaVersion` result exists so this branch is
    reachable rather than swallowed as `NaN`.

    If it is older or absent, take the copy **before** the first migration statement runs.
    `migrateToLatest`'s own docblock states why: the checksum guard catches an edited migration, but a
    copy is the recovery path if a migration fails partway on this driver's non-transactional-DDL
    adapter. Checkpoint the WAL before copying so the snapshot is complete rather than missing
    committed pages held in the sidecar — `03-02` turned WAL on, which makes this a real hazard rather
    than a theoretical one. A copy that cannot be written is a refusal, not a warning: the whole point
    is that the recovery path exists before the risky operation, so proceeding without it inverts the
    guarantee.

    Then call `migrateToLatest` with the migrations directory, surface its full `results` array on
    failure rather than reducing it to a boolean, and write `schema_version` through
    `metaRepository.setSchemaVersion`.

    **`reconcileRepos`.** For each entry in the daemon config's `repos`, call `reposRepository.upsert`.
    Configuration is already the trust anchor — daemon-only backend and credential selection exists
    precisely because repo-supplied files are untrusted — so repository identity belongs there too,
    and the table is a projection of the file. A repository in the table but absent from the config is
    **left in place** and logged at `info`: features may still reference it, and a config edit is not
    a delete instruction. `adl repo add` was rejected for v1 because it would turn the watched-repo
    set into database state with no file to review.

    Wire the sequence into `src/daemon.ts`'s startup, ahead of everything the tracer already does
    there. A refusal must exit before the API server binds.

    refuse-newer case asserts on file bytes, not on a flag — read the file before and after and
    compare digests, because "wrote nothing" is the claim that matters and a return value cannot prove
    it. The copy-first case asserts the copy's digest equals the original's pre-migration digest.
  </action>

    **`src/boot/orphans.ts`.** `lease_owner` records the worker's **PID and process start time**, and
    the boot-time kill verifies the start time still matches before signalling. PIDs are reused, so a
    stale PID may belong to an unrelated process by the time the daemon restarts; start time is the
    standard discriminator and makes the kill safe by construction. This matters disproportionately
    because ADL is installed on other teams' infrastructure — a control plane that `SIGKILL`s an
    unrelated process on restart is not shippable.

    Encode both values into the existing `lease_owner` TEXT column as JSON. No column is added, so
    `FEATURES_COLUMNS`, `TABLE_COLUMNS`, and the bidirectional drift test are untouched. Export
    `LeaseOwnerRecord`, `encodeLeaseOwner`, `decodeLeaseOwner`, and update `03-04`'s dispatcher to
    write the encoded form.

    `readProcessStartTime(pid)` on Linux reads `/proc/<pid>/stat` and takes field 22 (index 21). The
    value is in clock ticks **since system boot**, not wall-clock time, so it is meaningful only
    within one boot session — which is exactly D-14's use case, a daemon comparing against a value it
    or its predecessor recorded during the current uptime. Do not persist or compare these values as
    though they were portable identifiers across a host reboot; state that in the docblock, because
    the failure mode is a PID-reuse test that passes locally and produces false-positive kills after
    a CI runner reboots between batches.

    **Windows degrades, visibly.** There is no `/proc`. Per `03-RESEARCH.md` Open Question 1's
    recommendation and Phase 2's D-05/D-18 precedent, take the documented-degradation path:
    `readProcessStartTime` returns an unavailable result on Windows, and `killBootOrphans` treats
    unavailable start time as **not attributable** — it does not signal, it logs, and it reports the
    PID as skipped. Not signalling is the safe direction: leaving one orphan running is recoverable
    by an operator; killing an unrelated process on someone else's infrastructure is not. Do not add a
    PowerShell shell-out for this; it would put an exec call on the boot path for a guarantee the
    deployment target already has, and research recorded that mechanism as unverified (assumption A1).
    Record the degradation in `packages/manager/README.md` — an operator running the daemon on Windows
    should learn this from documentation rather than from a log line.

    `killBootOrphans` binds `processIsAlive` from `@adl/workspace` rather than writing a second
    liveness probe; that module's own comment warns against two probes that can disagree.

    **Boot order (D-13).** On startup the manager expires every lease and kills any still-running
    orphan worker **before** requeueing. That order is the point: no orphan from the previous daemon
    can race a replacement worker inside the same worktree, which is the one scenario D-04's
    `child.on('exit')` fast path structurally cannot cover, because the new manager has no child
    handle for a process it did not spawn. Re-adopting orphans was rejected — `fork()` IPC channels do
    not survive the parent, so it would need an entire second control channel.

    **`src/boot/shutdown.ts`.** `gracefulShutdown(deps)` in the order D-37 fixes: stop dispatch, stop
    the workers, close the server, flush, exit. Stopping a worker uses the amended D-28 mechanism —
    an IPC `soft_stop` message, then `SIGKILL` after `worker_stop_grace_ms` — for the reason recorded
    in `03-04`'s amendment: on Windows a `SIGTERM` to a forked child is emulated by unconditional
    forceful termination and runs no handler, so an OS-signal implementation would deliver no grace
    period at all on one of the two platforms D-33 requires CI to cover. Factor the per-worker
    escalation into one helper so `03-07`'s `adl kill` and this shutdown path share it rather than
    drifting.

    Register the handler on `SIGTERM` and on `SIGINT`. The HTTP server's `close` is called after the
    workers are stopped, so an in-flight status request still gets an answer.

    **Tests.** `test/boot/orphans.test.ts` covers encoding, the start-time match, the mismatch, and the
    dead-PID case, using the platform helper to skip the `/proc` assertion with a stated reason where
    it has no subject. The mismatch case is the load-bearing one and must run on Linux: fork a real
    child, record its PID with a deliberately wrong start time, and assert `killBootOrphans` leaves it

    `test/boot/daemon-restart.test.ts` is ROADMAP criterion 4: start a daemon against a temp database,

    `usage_events` are unchanged, every lease was expired at boot, and `feature_events.seq` for each
    feature is a contiguous sequence with no gap and no duplicate.
