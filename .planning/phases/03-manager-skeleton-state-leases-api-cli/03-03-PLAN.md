## The `fork()`-vs-exemption question is settled, not open

`03-CONTEXT.md` § `<code_context>` flags for the planner: *"the manager's `fork()` of the worker
needs an explicit decision about whether it goes through this path or earns a second exemption."*

It is decided, by the codebase itself, and both statements were verified by direct read:

- `eslint.config.js:21` — the architecture-rule table's "Extended by" column for the spawn ban reads
  *"Phase 3, when the manager→worker `fork()` seam lands as a named export of `packages/workspace`
  rather than as a second exemption"*.
- `eslint.config.js:218` — `SPAWN_MESSAGE` itself reads *"The Phase 3 manager→worker seam is not an
  exception: fork() lands as a named export of packages/workspace too, so the exemption count stays
  at one."*
- `eslint.config.js:318` — `WORKSPACE_EXEMPTION` is `[mod('packages/workspace/**/*')]`, which already
  covers the new file. Its docblock states plainly that a second entry "makes success criterion 2
  false while the rule still looks like it is enforcing something, which is strictly worse than
  having no rule at all".

**Do not add an exemption for `packages/manager`.** This plan's second task exists to prove that
none was needed.
</settled_question>

  <behavior>
    - `forkWorker` given a path to a Node module returns a handle whose `child` has a non-null `send` method — the IPC channel is open.
    - A message sent from the parent reaches the child, and the child's reply reaches a parent-registered message listener.
    - The child's stdout and stderr are piped to the caller rather than inherited by the daemon's own streams.
    - The child's environment contains only the keys `forkWorker` put there: a variable set in the parent process but absent from the options and from the allowlist is not visible to the child.
    - Forking a path that does not exist rejects or emits an error carrying that path, rather than leaving a handle in an indeterminate state.
    - The returned handle exposes the child's pid.
  </behavior>
  <action>
    Create `packages/workspace/src/exec/fork.ts` as a **sibling** of `run.ts`, not a modification of
    it. `run` is execa-specific; `fork()` is a different primitive, and wrapping `fork()` in an execa
    call loses the IPC channel that D-01's whole heartbeat design depends on.

    Export `forkWorker(entryPath: string, options: ForkWorkerOptions): ForkedWorker`.
    `ForkWorkerOptions` carries at minimum: `argv` (arguments passed to the child), `cwd`, `env`
    (explicit key/value pairs the caller wants the child to have), and `execArgv`. `ForkedWorker`
    carries at minimum: `child` (the `ChildProcess`), `pid`, and the piped `stdout`/`stderr` streams.

    Import `fork` from `node:child_process`. This file is inside `packages/workspace/**`, which
    `WORKSPACE_EXEMPTION` already covers — no eslint change is required or permitted.

    Pass `stdio` as `['ignore', 'pipe', 'pipe', 'ipc']`. The fourth slot is what keeps the IPC
    channel; the two `pipe` slots are what let the manager attach a pino child logger to the worker's
    output instead of interleaving it into the daemon's own stream, and they are what a later phase's
    transcript streaming reads from.

    Construct the child's environment explicitly. Do not spread `process.env`. Export a
    `WORKER_ENV_ALLOWLIST` naming the small set of parent variables that legitimately cross (the
    platform essentials a Node process needs to start — `PATH` and, on Windows, the variables Node
    itself requires), and merge `options.env` over it. WORK-06 says credentials never enter the
    worker's ambient environment: the daemon holds forge tokens and model API keys, and a spread of
    `process.env` here would hand every one of them to a process whose entire job is to run other
    people's code. `buildChildEnv` in `env.ts` solves the adjacent problem for agent children with a
    scratch `HOME` and is scoped to an `ExecSpec`; state in the docblock why `forkWorker` builds its
    own smaller set rather than reusing it, so the divergence is a recorded decision rather than an
    oversight.

    Write the header docblock in `run.ts`'s style: state that this is the second and last
    process-launch primitive in the repository, that it lives here for the reason recorded at
    `eslint.config.js:218`, and that the exemption count stays at one. Restate the `ExecOwner`
    reasoning as it applies here: the worker is an ADL-owned child, so it is deliberately not
    dropped to the unprivileged worker user — the drop applies to the agent processes the worker
    itself launches through `run()`, one layer down.

    Do **not** implement stop/kill escalation here. That is manager policy (D-28 as amended), belongs
    in `@adl/manager`, and putting it in the workspace package would make the workspace responsible
    for a lifecycle it does not own.

    Add `forkWorker` and its two types to `packages/workspace/src/index.ts` with a "why public"
    comment in the established style, stating that the manager's supervision seam is public
    precisely so that it does not become a second exemption.

    Create `packages/workspace/test/fixtures/echo-worker.js` — a plain Node module that registers a
    `process.on('message')` handler, echoes what it receives back through `process.send`, and writes
    one line to stdout and one to stderr on start. Keep it dependency-free and plain JavaScript so it
    needs no build step to be forkable from a test.

    Write `packages/workspace/test/exec/fork.test.ts` covering the behaviour list. The environment
    case is the load-bearing one: set a distinctive variable in the test process, fork without
    naming it, and assert the child reports it absent.
