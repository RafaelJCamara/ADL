<assumption_delta_decision>
## Assumption-delta decision — "concurrency is configurable"

The detector fired on the `chosen` family, against the ROADMAP phrase *"concurrency is configurable
and defaults to one feature in flight"*, asking whether a configuration decision has become a
modeling decision.

**The noun that is now primary:** *the concurrency cap* — a single global limit, with an optional
per-repository override.

**Decision: `no-change`.** Concurrency moving from implicit-1 to configurable is a parameter, not an
identity noun. The substantive half of the signal is D-15's introduction of a **global cap plus an
optional per-repo cap**, which is a genuine singular-to-plural move on "the cap". Two readings were
available:

1. A single global limit with an optional named override field —
   `concurrency: { global, per_repo? }`, checked at dispatch as a conjunction of two named
   predicates.
2. A general "concurrency scope" collection of which global is one instance —
   `[{ scope: 'global', limit }, { scope: 'repo', id, limit }]`, checked by walking the collection.

Reading 1 wins. EXEC-05 asks literally for one number ("Maintainer sets concurrency; it defaults to
one feature in flight"), and the roadmap's "run CI at concurrency 3" reads as a single global value.
Reading 2 is a generalization with exactly one non-global instance today, no requirement asking for a
third scope, and no stated precedence or inheritance rules for scopes to resolve against — a
collection whose only member is the thing you already had is a shape looking for a use case.

**What would force a promote later:** a third scope appearing (per-forge, per-agent-backend,
per-host), or the per-repo cap needing precedence or inheritance rules of its own. At that point
"concurrency scope" becomes the primary noun and the global cap becomes the `scope: 'global'` row.
Until then the conjunction of two named predicates is both smaller and more readable at the call
site.

This is not accepted debt — reading 1 is a complete answer to the requirement as written, not a
deferred version of reading 2.
</assumption_delta_decision>

<amendment_reference>
## D-28 is implemented as amended — IPC first, SIGKILL last

`stopWorker` in this plan does **not** send `SIGTERM`. The full amendment, with sources, is recorded
in `03-04-PLAN.md` § `<amendment>`. In short: on Windows, `child.kill('SIGTERM')` on a forked child is
emulated by unconditional forceful termination and runs no handler, and execa's `forceKillAfterDelay`
is a documented no-op there and in any case does not reach a `fork()`ed child. D-28's intent — a
bounded graceful window, then unconditional termination — is delivered by an IPC `soft_stop` message
over the channel D-01 already uses, escalating to `SIGKILL`, which is the one signal that is reliably
forceful on both platforms. D-33 requires the recovery suite on Windows, so this is the difference
between a grace period and a grace period that silently does nothing.
</amendment_reference>

<flagged_assumptions>
## Flagged assumptions — OBS-03 and OBS-04 edge-probe rows (unresolved)

Both were classified **`unclassified`** by the spec-less edge probe and stay `unresolved`; neither is
auto-resolved with a backstop marker. A reviewer should rule on each.

**OBS-03** — *"Maintainer can pause work."* The unstated boundary is **scope and persistence**. D-26
fixes the semantics (dispatch stops; in-flight finishes its round and parks) but nothing states
whether a global pause survives a daemon restart. This plan holds the global pause flag in memory
only, so a restart resumes dispatch. That is a real behavioural choice — an operator who pauses and
then restarts the daemon gets work starting again — and it is an assumption, not a decision. A
persisted pause would be a `meta` row and a boot-time read.

**OBS-04** — *"Maintainer can kill a single feature, everything in one repo, or everything."* The
unstated boundary is **what "everything" includes**. This plan reads `--all` as every feature
currently holding a lease plus every feature in `queued`, across every watched repository — that is,
it both stops what is running and parks what is waiting. The alternative reading, that `--all` stops
only what is in flight and leaves the queue intact, is equally consistent with the requirement text
and would behave very differently for an operator trying to bring the host to a stop. Recorded as an
assumption.
</flagged_assumptions>

    Add cap enforcement to `dispatchOnce`. The cap is a **global** number with an **optional
    per-repository** override, checked as a conjunction of two named predicates — see

    per-repo cap proves insufficient.

    `adl kill` remains the deliberate tool for stopping now. Implement the over-cap case explicitly —
    when in-flight exceeds the cap, dispatch nothing and revoke nothing — and test it, because the
    tempting implementation is to shed load.

    budget gate needs, which must be evaluated before the next agent turn is dispatched rather than
    after it has been paid for; establishing the shape here means Phase 6 extends a predicate instead
