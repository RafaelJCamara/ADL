## Flagged assumptions — EXEC-03 and EXEC-04 edge-probe rows (unresolved)

Both were classified **`unclassified`** by the spec-less edge probe. An `unclassified` row is never
auto-resolved with a backstop marker, so both stay `unresolved` and are surfaced here rather than
dropped. A reviewer should rule on each.

**EXEC-03** — *"A worker killed mid-loop is detected and its feature recovered, with committed work
preserved and burned spend retained on the ledger."* The unstated boundary is **what counts as
committed**. This plan reads "committed work" literally as git commits reachable on the feature
branch, because Phase 2's worktree lifecycle is what makes that the durable artefact. Work the
worker had written to the working tree but not committed when it was killed is **not** preserved by
any mechanism here — it survives only incidentally, in the re-attached worktree, and D-10's
replay-from-stage-0 means it is not trusted as evidence either way. That reading is an assumption,
not a stated requirement.

**EXEC-04** — *"A resumed zombie worker cannot write stale results over newer state."* The unstated
boundary is **how long a zombie may be tolerated**. This plan rejects and counts stale writes
indefinitely — there is no expiry after which a zombie's message is ignored silently instead of
being logged, and no cap on the rejection counter. That is deliberate (D-09: a real fencing bug
should be visible in production), but it means a permanently wedged zombie holding a live IPC
channel produces an unbounded log stream. No decision covers that case; it is recorded here.
</flagged_assumptions>

    tick compare rows against a moving target, and it would break the caller-supplied-timestamp
    discipline `TransitionCtx.at` already establishes.

    not `croner`. The reaper's cadence is a numeric interval read from `heartbeat_interval_ms` /

    scheduling and its sub-100ms resolution is unverified (recorded as research assumption A2).

    latency; the reaper stays the backstop for the two cases `exit` structurally cannot cover, which
    are a manager that itself restarted (no child handle to listen on) and a worker wedged but alive.

    `false`. This is defence in depth, not the guarantee: fencing at the database is the guarantee,
    but a worker that stops on its own never races a replacement worker inside the same worktree, so
    the file-level conflict never arises in the first place.

    Wire `startReaper` into `src/daemon.ts`'s startup sequence and its `stop()`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| zombie worker → persisted feature state | A process whose lease was reassigned still holds a live IPC channel and can send |
| crash-recovery path → adopter's committed work and spend ledger | Recovery decides what survives a crash |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-3-06 | Tampering | supervisor message handler `checkFence` | high | mitigate | `checkFence` runs before any repository write for every lease-scoped message kind, and `03-02`'s `WHERE lease_token = ?` predicate holds independently. Two separate tests prove each half — the D-31 zombie scenario for the handler, and a direct repository call with a stale token for the predicate |
| T-3-13 | Denial of Service | reproducibly crashing feature | high | mitigate | `MAX_CONSECUTIVE_CRASHES` of 3 escalates instead of recovering a fourth time (D-11); without a ceiling a crash-looping feature holds a worktree, a process slot, and eventually paid agent turns indefinitely |
| T-3-27 | Repudiation | silently dropped stale write | medium | mitigate | Every rejection emits a `warn` naming feature id, presented token, and current token, and increments a counter surfaced through `GET /features` (D-09); silent dropping was explicitly rejected because a real fencing bug would then be invisible in production |
| T-3-28 | Tampering | recovery discarding committed work or ledger rows | high | mitigate | Recovery re-attaches the existing worktree through `workspace_handle` and writes no `usage_events` row; the integration test asserts the commit is still reachable and the ledger rows are unchanged, so a recovery path that started deleting would turn the suite red |
| T-3-29 | Denial of Service | unbounded stale-rejection logging from a wedged zombie | low | accept | Recorded as an EXEC-04 flagged assumption above; no decision covers a rejection-rate cap, and D-09's visibility requirement argues against silencing.
