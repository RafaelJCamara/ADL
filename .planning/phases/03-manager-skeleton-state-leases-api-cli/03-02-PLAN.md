    `nowIso`, and every lease timestamp accepted as a parameter goes through `assertIsoTimestamp`.
    The reason is a real correctness property rather than tidiness: `lease_expires_at < ?` is a
    lexicographic string comparison in SQLite, and it coincides with chronological order only because
    every writer uses the same fixed-width zero-padded format. Nothing at the schema level enforces

    `Number(result.numUpdatedRows) === 1` returned as a boolean. Never throw for a lost race:
    `compareAndSwapState`'s own JSDoc explains why a caller-visible `false` beats an exception, and
    D-09 applies the same reasoning to the fence.

      same predicate; it exists separately so a log line can distinguish a worker that finished from

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-3-06 | Tampering | `featuresRepository` lease-scoped writes | high | mitigate | Every lease-scoped `UPDATE` carries `WHERE lease_token = ?` with `leaseToken` a required non-optional parameter (D-06, D-08); the data-layer half of the fence holds even if a future code path bypasses the manager's message handler, and `packages/db/test/lease.test.ts` proves it by calling the repository directly with a stale token |
| T-3-20 | Tampering | `lease_expires_at` timestamp format drift | medium | mitigate | One `nowIso()` writer plus `assertIsoTimestamp` on every accepted timestamp; a differently formatted string would silently break the lexicographic-equals-chronological property the reaper's `<` predicate depends on |
