<amendment>
## Amendment to D-28 — the grace period is an IPC message, not an OS signal

**D-28 as written:** *"Workers are stopped with SIGTERM, then SIGKILL after a configurable grace
period (~10s default) … `execa` was chosen partly for `cancelSignal` and `forceKillAfterDelay`,
which is exactly this pattern with cross-platform child cleanup already handled."*

**Why the mechanism does not survive contact with the required platforms.** `03-RESEARCH.md`
§ Pitfall 1 and § Pitfall 3 establish two facts, each corroborated by two independent sources:

1. On Windows there is no POSIX signal delivery. `child.kill('SIGTERM')` on a forked child is
   emulated by unconditional forceful termination, giving the child **no opportunity to run a
   handler** — behaviourally identical to `SIGKILL`. (Node's own `child_process` documentation,
   cross-checked against `nodejs/node#12378`.)
2. `execa`'s `forceKillAfterDelay` is documented as a **no-op on Windows** for exactly that reason —
   and in any case it does not apply here, because execa's escalation options govern only processes
   execa itself spawned. The worker is launched with `child_process.fork()` and is a plain
   `ChildProcess`, not an execa subprocess. Execa in this repository is confined to
   `packages/workspace/src/exec/run.ts` and never launches the worker.

D-33 requires the recovery suite to run on Windows in CI, so this is not theoretical: implemented
literally, D-28 would assert two different behaviours under one decision, and the Windows leg would
either fail or — worse — pass while the grace period silently did nothing.

**What is amended, and what is not.** The decision's *intent* stands unchanged: a bounded graceful
window in which the worker aborts its stage and releases the worktree cleanly, then unconditional
termination. Only the *mechanism* changes:

| | D-28 as written | As implemented |
|---|---|---|
| Graceful signal | `child.kill('SIGTERM')` | `child.send({ t: 'soft_stop', … })` over the existing `fork()` IPC channel |
| Grace period | configurable, ~10s default | unchanged — `worker_stop_grace_ms`, 10000 default |
| Hard stop | `child.kill('SIGKILL')` | unchanged — `SIGKILL` is the one signal that is reliably forceful on both platforms |
| Escalation owner | execa | `@adl/manager`'s own helper; execa cannot reach a forked child |

**Why this is the smallest possible change.** D-01 already routes the heartbeat over this channel and
already argues that a dead IPC channel is a liveness signal in its own right; D-05 already has the
worker self-terminating on a fatal IPC condition, which is the exact handler `soft_stop` invokes. No
new capability is introduced — one new message kind in a union `03-CONTEXT.md` already left to the
planner's discretion ("The concrete IPC message union between manager and worker — its typed
contract is the planner's to design"). `03-RESEARCH.md` § Pattern 2 recommends precisely this.

**Where it lands:** the `soft_stop` kind is defined in this plan's IPC protocol so the union is
complete from the first commit; the escalation helper that uses it is built in `03-07`
(`stopWorker`), and daemon shutdown reuses the same helper in `03-06`.
</amendment>

## Flagged assumption — EXEC-02 edge probe row (unresolved)

The spec-less edge probe classified EXEC-02 (*"Worker runs as a separate OS process holding a lease
on one feature"*) as **`unclassified`** — the probe could not place it in a shape category and its
guidance is "review manually". Per protocol an `unclassified` row is **never** auto-resolved with a
backstop marker, so it stays `unresolved` and is surfaced here rather than silently dropped.

**The specific ambiguity a reviewer should rule on:** EXEC-02 says a worker holds a lease on *one*
feature. Nothing in REQUIREMENTS.md or CONTEXT.md states what happens to the one-to-one mapping in
the two directions that are not simply "one worker, one feature":

- Can a feature ever be served by two worker processes at once? This plan's answer is no, structurally:
  the dispatcher forks only after `acquireLease` returns `true`, and `acquireLease` admits only an
  unheld or expired lease. That is an implementation answer, not a stated requirement.
- Can one worker process ever hold two leases? This plan's answer is no — the supervisor keys its
  active-worker map by feature id and the worker entry accepts exactly one `assign` message per
  process lifetime, rejecting a second. Again an implementation answer.

Recorded as an assumption, not a decision. It is carried into `03-09`'s scenario test, whose closing
assertion "no feature was ever double-leased" is the observable form of the first half.
</flagged_assumptions>

  <decision>
    D-19 is already locked: the API binds loopback by default and is protected by a shared bearer
    token in the daemon config. That is not being re-asked. What is not yet decided — and what this
    plan is about to make permanent — is **where the token comes from, how it is stored, and whether
    `GET /health` is exempt from it**.
  </decision>
  <context>
    D-19 is rated **one-way, in the safe direction**: shipping a control plane without auth and
    adding it later breaks every adopter script that already exists. The corollary is that the
    *shape* of the auth ships at the same time and is equally sticky — the token's location on disk
    becomes an operator-facing convention, and whether `/health` needs a token determines whether an
    external supervisor (systemd, a container healthcheck, a load balancer) can probe the daemon
    without being handed a credential that can also pause and kill every feature on the host.

    Undoing the storage choice later means every adopter's deployment scripts and any documentation
    change together. Undoing the `/health` choice later either breaks probes (tightening) or widens
    an unauthenticated surface on a control plane (loosening).
  </context>
  <options>
    <option id="option-a">
      <name>Daemon-generated token in the config file; every route authenticated including /health</name>
      <pros>Zero-configuration first run — the daemon mints a token with `crypto.randomBytes(32)` on
      first start and writes it into the daemon config file, and the CLI reads the same file, so
      `adl status` works immediately after `adl daemon start`. One rule with no exceptions is the
      easiest thing to reason about and the easiest thing to keep true.</pros>
      <cons>An external supervisor cannot probe readiness without the full control-plane credential.
      The daemon writing to its own config file blurs "configuration is the trust anchor" (D-35/D-36)
      — the file is no longer purely operator-authored.</cons>
    </option>
    <option id="option-b">
      <name>Daemon-generated token in the config file; GET /health unauthenticated, returning only liveness</name>
      <pros>Same zero-configuration first run. A container healthcheck, systemd readiness probe, or
      `curl` smoke test works with no credential. The exempt endpoint returns only a status word and
      the schema version — nothing about features, spend, repositories, or the token itself — and the
      server is loopback-bound, so the unauthenticated surface is one process boundary wide.</pros>
      <cons>One exception in the auth rule is one thing a future contributor can widen. It needs a
      test asserting the exemption list has exactly one entry, or it will grow.</cons>
    </option>
    <option id="option-c">
      <name>Operator-supplied token only — the daemon refuses to start without api.token</name>
      <pros>The config file stays purely operator-authored, which keeps D-35/D-36's trust-anchor
      story clean. There is no path by which a token ADL generated ends up in a file an operator
      thought they controlled.</pros>
      <cons>First run fails with a configuration error rather than working, which is the opposite of
      what DIST-01 (Phase 18) will ask for. Every adopter has to be told how to generate a good
      token, and some will pick a bad one.</cons>
    </option>
  </options>

    - Constant-time comparison (`crypto.timingSafeEqual`) is used regardless of which option is chosen — that part is not up for decision.
  </acceptance_criteria>

    Build the single vertical path. This is production code, not a prototype — a stub is permitted
    only where it can later be filled without an architectural change.

    **`src/ipc/protocol.ts`.** Two Zod discriminated unions on a `t` discriminator, types via
    `z.infer`, following the `.strictObject` + `.meta({ id })` convention `effective-config.ts`
    establishes. Worker-to-manager kinds: `ready` (carries `leaseToken`, `pid`, `startedAt`),
    `heartbeat` (`leaseToken`, `at`), `stage_result` (`leaseToken`, `roundId`, `stageIndex`,

    thing that would call an agent swapped out. There is deliberately **no** `--fake` flag and **no**
    environment variable selecting a runner — a flag on the shipped binary is a foot-gun on a real
    installation, and injection through a parameter means Phase 4 replaces one module rather than
    deleting a harness. In this phase the production `StageRunner` is a real implementation that
    reports a named "no agent backend configured in this phase" outcome; it is a functionality gap,
    not an architectural one.

    `runWorker` registers `process.on('message')`, validates every inbound message through the
    manager-to-worker schema, accepts exactly one `assign` per process lifetime (a second is
    rejected and logged), starts an interval that sends `heartbeat` at `heartbeatIntervalMs`, runs
    the injected stage runner, sends `stage_result`, and exits. On `soft_stop` it aborts the current
    stage and exits — that handler is the same path D-05's self-termination uses, which is why the
    amendment above costs no new capability. On a dead IPC channel (`process.disconnect` or a send
    failure) it exits non-zero. This module **must not import `@adl/db`** — see Task 3.

    **`src/worker-supervisor/supervisor.ts`.** `createSupervisor(deps)` returns an object holding a

    arrive only on the channel the manager itself opened, so the supervisor's own bookkeeping is the
    trust boundary — do not conflate two workers' channels in one handler closure.
